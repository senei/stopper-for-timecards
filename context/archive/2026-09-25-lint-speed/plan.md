# Lint Speed Implementation Plan

## Overview

Stop ESLint and Prettier from processing the Wrangler-generated `workers/purge-job/worker-configuration.d.ts`, which accounts for about half of the measured lint time, and prove the saving with matched before/after timings. The slow cold-start runs (4 to 15 minutes) are a separate, still-unexplained problem and are deliberately not part of this change.

## Current State Analysis

- `npm run lint` lints about 47 files with type-aware rules and Prettier-inside-ESLint (`eslint.config.js:16-23`, `:92`). In the primary checkout at `c4bdfef`, a full uncached run took 33 s (direct `node`), 45 s (`npm run lint`, empty cache) and 12 s with a warm cache (`context/changes/lint-speed/research.md`).
- `workers/purge-job/worker-configuration.d.ts` is a tracked, 15,384-line file generated by `wrangler types`, with `/* eslint-disable */` in its header (`workers/purge-job/worker-configuration.d.ts:1-3`). That comment hides reports but does not stop rules from running. It took 20.9 s of 40.4 s of parse-plus-rule time in one full run (52%), and Prettier alone spent 20.1 s of its 22.3 s on it (90%).
- Ignoring it with `--ignore-pattern` took a full uncached run from 33 s to 20 s (one run each).
- There is no `.prettierignore`. `npm run format` (`prettier --write .`, `package.json:12`) and the commit hook (`.husky/pre-commit` runs `npx lint-staged`, which runs `eslint --fix` on staged `*.{ts,tsx,astro}`, `package.json:62-68`) also touch the file whenever it is formatted or staged.
- Nothing in `package.json`, CI or the docs runs `wrangler types`; the file has been committed twice (`57fc5e6`, `d090e58`), so it is regenerated by hand and rarely.
- Verified while planning: `npx eslint <ignored file>` prints a warning and exits 0 (tested on `.claude/skills/10x-research/scripts/metadata-guard.mjs`), so `lint-staged` will not block a commit; `npx prettier --file-info` reports the generated file as `"ignored": false` today and `dist/index.js` (gitignored) as `"ignored": true`.

## Desired End State

ESLint and Prettier both skip `worker-configuration.d.ts`, the file stays tracked and unchanged, and `npm run lint` still exits 0 with no problems. `context/changes/lint-speed/measurements.md` records three timed full uncached lints before and three after, and the after-median is strictly lower than the before-median.

### Key Discoveries:

- Ignore list to extend: `{ ignores: [".claude/**"] }` at `eslint.config.js:85`, next to the `.gitignore`-based ignores at `:83`.
- Prettier 3 reads `.gitignore` and `.prettierignore` by default, so a new `.prettierignore` must not lose gitignored paths; this is checked with `prettier --file-info dist/index.js`.
- Timings on this machine vary a lot between runs (the same uncached lint took 253 s once, then 61 s, 33 s), so a single before/after pair proves nothing; the comparison uses the median of three runs.

## What We're NOT Doing

- **Investigating cold-start slowness.** Why some fresh-worktree runs take 4 to 15 minutes is untested and belongs to a separate change. Decided with the user in planning.
- **Untracking the generated file** or adding a `wrangler types` step to `package.json`, CI or the docs. Decided with the user in planning (the file stays tracked and is ignored by both tools).
- Removing `eslint-plugin-prettier`, dropping type-aware rules, changing the Astro `project:` setting, or changing the `--cache` flags: the measurements do not support them.
- Machine-level changes (for example a Windows Defender exclusion) and CI changes.
- A fixed time target: success is defined as an improved median, not a number. Decided with the user in planning.

## Implementation Approach

Two phases: measure first, then change and re-measure, so the comparison is honest. The change itself is two ignore entries. The glob `**/worker-configuration.d.ts` is used instead of the single path because Wrangler uses that file name for every worker it generates types for.

## Critical Implementation Details

- **Measurement conditions.** Run the baseline and the after-runs in the same checkout, one at a time, with no other heavy processes (dev servers, database resets, other sessions' builds) running. Discard one warm-up run before the three timed runs: the first full run in a session took 253 s and an identical repeat 61 s, and the warm-up absorbs that. If a fresh worktree is used, run `npm ci` and `npx astro sync` first (`context/foundation/lessons.md:54-59`).
- **Timed command.** Use `node node_modules/eslint/bin/eslint.js . --no-cache`, not `npx` (about 9 s of extra start-up) and not the cached `npm run lint`; time it with `date +%s` before and after.
- **"Improved" means strictly lower.** Equal medians count as not improved.

## Phase 2: Ignore the generated file and re-measure

### Overview

Add the ignore entries, confirm both tools honour them, and record the after-timings next to the baseline.

### Changes Required:

#### 1. ESLint ignore

**File**: `eslint.config.js`

**Intent**: Stop ESLint (and therefore `eslint-plugin-prettier` and the type-aware rules) from processing Wrangler-generated type files.

**Contract**: Add `"**/worker-configuration.d.ts"` to the existing ignores entry near `eslint.config.js:85` (`{ ignores: [".claude/**"] }`), with a one-line comment saying these are generated by `wrangler types` and that the file-level `eslint-disable` header does not stop rules from running. No other config entries change.

#### 2. Prettier ignore

**File**: `.prettierignore` (new)

**Intent**: Stop Prettier (CLI, `npm run format` and the `eslint-plugin-prettier` rule) from formatting the generated file.

**Contract**: One entry, `**/worker-configuration.d.ts`, with a short comment. Prettier 3 reads both `.gitignore` and `.prettierignore` by default, so gitignored paths such as `dist/` must still be reported as ignored.

#### 3. After-measurements

**File**: `context/changes/lint-speed/measurements.md`

**Intent**: Record the after-timings in the same format as the baseline, and the comparison.

**Contract**: An "After" section with three wall-clock times, exit codes and problem status, its median, the baseline median, and one line stating whether the median improved (strictly lower).

### Success Criteria:

#### Automated Verification:

- ESLint reports the generated file as ignored and exits 0 for it (as `lint-staged` will pass it): `npx eslint workers/purge-job/worker-configuration.d.ts`
- Prettier reports the generated file as ignored: `npx prettier --file-info workers/purge-job/worker-configuration.d.ts`
- Prettier still ignores gitignored paths: `npx prettier --file-info dist/index.js`
- Full lint passes: `npm run lint`
- Three timed full uncached lints after the change all exit 0 with no problems reported: `node node_modules/eslint/bin/eslint.js . --no-cache`

#### Manual Verification:

- The after-median recorded in `context/changes/lint-speed/measurements.md` is strictly lower than the baseline median (equal counts as not improved)

## Testing Strategy

### Unit Tests:

- None: this is tool configuration with no application code.

### Integration Tests:

- `npx eslint` and `npx prettier --file-info` on the generated file (ignored), on a gitignored path (still ignored) and `npm run lint` (exit 0).

### Manual Testing Steps:

1. Run the baseline (one warm-up, three timed) before changing anything, and record it.
2. Apply the two ignore entries, run the checks above, then the three timed runs again.
3. Compare the medians in `measurements.md`.

## Performance Considerations

The expected saving is about 13 s on a 33 s full uncached run (one measurement); the plan does not promise a number. The commit hook and `npm run format` also stop spending about 20 s on the file when it is staged or formatted.

## Migration Notes

Configuration only; revert by deleting the two ignore entries. The change folder is currently uncommitted on `main` in the primary checkout, so commit it (or carry it into the worktree used for implementation) before Phase 1.
