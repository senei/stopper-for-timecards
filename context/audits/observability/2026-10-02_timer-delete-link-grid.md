# Observability audit — timer, delete, link, weekly grid + purge (2026-10-02)

## 1. TL;DR

- **Pages turn every backend failure into a friendly 503 and log nothing.** 13 bare `catch {` blocks; runtime-confirmed on the workspace and grid pages (R7, R12–R14): the user sees "Temporarily unavailable", the responder sees only a request line.
- **Error structure is destroyed at the data layer.** About 30 `throw new Error(\`x failed: ${error.message}\`)`with no`cause`; the PostgREST `code`/`details`/`hint`are gone before any logger runs (R1, R3, R5: code`XX000` never printed).
- **Failures are shaped like successes.** Action routes answer `303 → ?error=1`, lookup failures a null-body 503, unknown tokens a silent `rewrite("/404")`. The platform records a normal invocation; the only signal is a console line with no link id, no route and an identical string in six routes.
- **No shared reporting layer.** No middleware, no `500.astro`, no logger module; 14 inline `console.error` calls each silenced with `eslint-disable`. Nothing can add route, link id or release in one place.
- **Sign-up can fail completely and look like normal bot traffic.** `verifyTurnstile` returns `false` for a missing secret, a Cloudflare outage and a real rejection alike (static finding).
- **The purge job can only report on runs that happened.** A no-op purge records `success, 0 rows`, and a cron that never fires leaves no trace.

## 2. Capture model

How a failure travels from code to a human here:

- **Runtime:** Astro 7.3.2 SSR on Cloudflare Workers through `@astrojs/cloudflare` 14.3.1 (`astro.config.mjs`, `wrangler.jsonc:3` points `main` straight at the adapter). A second cron Worker, `workers/purge-job`.
- **Tracker:** none. No Sentry/OTel/etc. in `package.json` or `src`. The roadmap baseline says "no app-level error tracking".
- **Pipeline:** `observability.enabled: true` in `wrangler.jsonc:12` and in `workers/purge-job/wrangler.jsonc`, so Workers Logs collect console output and invocation outcomes.
- **Boundaries:** none of our own. No `src/middleware*`, no `src/pages/500.astro`, no global handler. The only catch is Astro's: `astro/dist/core/routing/handler.js:101` and `core/pages/handler.js:75` run `logger.error(null, err.stack || err.message || String(err))` and then render a **blank 500** (no error route exists). The `cause` chain is not logged.
- **Reporting inside the app:** `console.error("<static msg>:", err)` at 14 sites (`api/links.ts:53`, the six `link lookup failed` routes, five action-failure routes, `access-log.ts:31,35`) plus 3 in the purge worker. No `waitUntil`/fire-and-forget anywhere in `src`.
- **Durable records:** `access_log` (link-access audit, written by `logAccess`, never throws) and `job_runs` (purge outcomes).
- **Identity:** no release, SHA or environment tag in any code or either wrangler config.
- **Scrubbing/sampling:** none exist.

**Assumptions (outside the repo, not findings), all unconfirmed:**

- Workers Logs retention and any log-to-alert rules exist.
- Whether production Workers Logs record the full request URL, which contains the private `/w/<token>`.
- How production workerd renders `Error` arguments to `console.error`. Locally `Error` with `cause` prints message, stack and `[cause]`, and a plain object prints all fields (P9a/P9b).
- Free-tier log persistence for the purge Worker (a code comment at `workers/purge-job/src/index.ts:14` says it is not persisted).

## 4. Systemic root causes

1. **Pages treat a backend failure as UI state, not an event.** `catch {` with no binding, then `unavailable = true` and a 503: `src/pages/w/[token].astro:31`, `w/[token]/grid.astro:33,75`, `delete-account.astro:29`, `regenerate.astro:26`, `projects/[projectId]/delete.astro:28`. The lib layer throws specific messages (`week entries lookup failed: …`, `weekly-grid-query.ts:26`) and the page discards them. A returned 503 is an "ok" invocation. Explains F1, F3, F8, F14. Reasonable local decision: a friendly page instead of a crash.
2. **The data layer keeps only `error.message`.** `links.ts:14,41,63,83,106`, `projects.ts:26,60,92`, `timer.ts:70,91,110,127`, `weekly-grid-query.ts:26` and others. PostgrestError is a plain object, so `code`/`details`/`hint` never reach a logger, and the stack points at the wrapper (in the bundle, at `dist/server/chunks/…`). Explains F4, F11, F12.
3. **Failures are encoded as ordinary responses with no identity.** `303 → ?error=1` (`timer/*.ts`, `delete-account.ts:49`, `regenerate.ts:50`, `links.ts:53`), body-less 503s and silent `rewrite("/404")`. The log line is static and carries no `link.id`, route or operation although `link.id` is in scope. Explains F5, F6, F7, F9.
4. **No shared boundary or logger.** No middleware, no `500.astro`, no log module, 14 per-site `eslint-disable no-console`. Work after the guarded lookup (`getCurrentTimer`, `listProjects`, `getProject`) is unguarded and ends in Astro's blank 500. Explains F3, F13, F18.
5. **Expected and unexpected outcomes share a silent path.** Turnstile, cookie lookup, body parsing, cap/throttle/kill-switch and `logAccess` all swallow or return a default without a signal (`turnstile.ts:16-38`, `link-cookie.ts:40`, `api/links.ts:22-47`, `access-log.ts:19-21`). Explains F2, F8, F9, F10, F14.
6. **The purge job reports only what it ran.** `rows_affected: purge.data ?? 0` (`workers/purge-job/src/index.ts:33-43`), no staleness/absence reader anywhere in `src`, no stale-`running` reaper. Explains F20–F22.

## 6. Recommended fix order

Ordered by blindness removed per unit of effort. Privacy constraint throughout: log `link.id`, never the token, and keep `code`/`details`/`hint` but never request bodies or IPs.

1. **One logging helper plus fill every silent catch** (closes F1, F5-by-name, F8, F14, most of F7, part of F3). `src/lib/log.ts` with `logError(event, { route, linkId, op, err })` that serializes `message`, `code`, `details`, `hint`, `cause`, `stack` explicitly (P9c shows `String(err)` loses it all). Replace the 14 inline `console.error`s and the 13 bare catches. Smallest change with the biggest effect: the four pages marked **missed** become visible.
2. **Keep the cause at the lib boundary** (F4, F11, F12). A `DbError` carrying `code`, `details`, `hint`, `status` and `{ cause }`, used by `links.ts`, `projects.ts`, `timer.ts`, `weekly-grid-query.ts`. This also gives the `23503`/`23505` mapping something solid to check (constraint name).
3. **Turnstile as a discriminated result** (F2), plus the widget error/expired callbacks. This is the only finding where a total outage of sign-up is indistinguishable from normal traffic.
4. **A boundary**: middleware that logs `{route, method}` for uncaught errors, a `500.astro`, and wrap the post-lookup page work so it reaches the same 503 state (F3, F13, F18).
5. **Lifecycle and outcome events** (F9, F10, F7): one structured `warn`/`info` per `closed`/`busy`/`full`, regeneration, account delete and 404-by-reason; log when `createAdminClient()` is null; distinct `access_log` outcome for rotation. Beware double reporting with step 1 and the cardinality of route names.
6. **Purge worker** (F20–F22): validated result, cutoff and remaining-eligible count in `job_runs`, stale-`running` reaper, a staleness check that something actually reads.
7. **Decide on the token in platform request logs** (F17) and add release/env identity (F16). Needs a platform-side answer first.
